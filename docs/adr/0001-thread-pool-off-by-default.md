# 0001. 线程池默认关闭，只按需开启

- 状态：已接受
- 日期：2026-11-22

## 背景

v1.1 的 §3.1 L2 想把“每模块一条线程”换成“池化 + 模块亲和”，用来在模块数远大于核数时省线程、提高每核吞吐。实现和测量都在 PR #34 里。

硬约束是计数器单写者（`AGENTS.md` §5）：每个模块的 processed/dropped/join-expired/failed 只能有一个写线程。所以池化不能“谁空谁上”，只能把模块**固定**挂在某一槽（`slot = i * poolSize / modules`），本质仍是“每模块一条逻辑线程”，只是物理线程共享。

300 s × 2 次、同机（i7-14700KF，Windows MSVC 与 WSL2）的实测，p4/p8 相对 p0：

| 配置 | Windows | WSL2 |
|---|---|---|
| L4cap16 pool 4 | 3.015 M vs 2.879 M / 3.96 核（**104.8%**） | 3.633 M vs 3.742 M（**97.1%**） |
| L16cap8 pool 4 | 1.489 M vs 2.626 M / 15.55 核（**56.7%**） | 1.931 M（慢批区间） |
| L16cap8 pool 8 | 2.110 M vs 2.626 M（**80.4%**） | 2.573 M（慢批区间） |

浅链（4 模块）基本不交税，深链（16 模块）在 Windows 上仍然明显落后；同一个二进制在 WSL2 上还有批次间波动（见 §14.5）。

## 决定

1. `PipelineContext::WithThreadPoolSize()` 默认 **0**：0 表示维持 v1.0.x 的“每模块一条私有线程”，代码路径与 v1.0.1 完全一致（§14.2 的同机 A/B 落在噪声内）。
2. 需要省线程时显式开启；映射默认连续块（`kContiguous`），槽内下游优先。
3. 验收口径按平台分开：Windows 看 p0/p4，WSL2 看 p4；WSL2 深链 p0 只记录区间，不作为结论依据。

## 后果

- 默认路径零风险：不开启就与上一版本同一条路径，升级不需要重新评估。
- 收益依平台：Windows 深链开 pool 4 只有 56.7%，必须自评；Linux/WSL2 上开启基本免费。
- 线程数下降带来的可观测变化（`GetThreadPoolStats`、stop 顺序）只在开启时出现，不影响默认用户。

## 备选

- **默认开启**：否决。Windows 深链 −43%，且会让所有用户的停机和背压语义跟着变。
- **按平台自动选**：否决。同一台机器在 WSL2 上都能在快慢两批之间跳，自动选择等于不可预测、不可复现。
- **池化 + 模块可漂移（L1）**：否决。直接破坏单写者契约，需要把所有计数换成多写者协议，代价远大于收益。

## 什么时候该重看

- Windows 深链 pool 4 追到 p0 的 85% 以上（L2 剩余四项：完成信号、有界阻塞、格内轮转、计数可观测）；
- 或者出现“模块数 >> 核数”的真实用户场景，默认值成为负担。
