# 0002. Windows 深链池化的残余差距记为已知限制

- 状态：已接受（已知限制，不是待修 bug）
- 日期：2026-11-22

## 背景

`0001` 把池化定为 opt-in。开启后的实测里，浅链（4 模块）基本追平甚至反超，深链（16 模块）在 Windows 上仍然只有 p0 的 56.7%（pool 4）与 80.4%（pool 8），而 WSL2 上 pool 8 已在慢批区间内接近或超过 p0。

先把“是不是 bug”查清楚。300 s 窗口、两次重复、同机：

| 指标 | L16cap8 p0 | p4 | p8 |
|---|---|---|---|
| 吞吐 | 2.587 M～2.664 M | 1.489 M | 2.110 M |
| 核数 | 15.55 | 3.98 | 7.97 |
| p50 | 34.69 µs | 39.75 µs | 27.12 µs |
| cycles / 消息 | 20,249 | 9,138 | 12,909 |
| 每核吞吐 | 168.8 K | 374.2 K | 264.7 K |

`cycles/消息` 反而更低（9,138 vs 20,249）——每条消息更便宜，但同时在飞的少，所以总吞吐低。差距不在“每条消息更贵”，在“并行度不够”。

已排除的假设：

1. **调度等待**：p4 占用 3.98/4 核 = 99.5%，线程几乎一直在 CPU 上，调度等待不可能是主因。
2. **等唤醒**：`threadPoolStats` 显示 blocked 85.7%、idle 5.3%；off-CPU 采样（`sched:sched_switch`）在 7 条 worker 上只看到 `clock_nanosleep`，0 次 futex——不是“睡了等别人叫”。
3. **队列交接本身**：on-CPU 采样里 `PutIfSpace` 占 18–21%，p0 与 p4 共付，不是池化独有。

剩下的解释是一致的：**背压 + 槽内串行**。每个槽一轮只推进少量模块，被下游满边挡住时整槽空转（`Pause()`）；浅链轮转一圈很快，深链每跳都要等一个槽轮次。

## 决定

1. 承认这是已知限制，不在 1.1 继续投入；`§14.5` 与 `design/thread-pool.md` 明确写清适用面。
2. 文档给出推荐：Linux/WSL2 可以开；Windows 深链需要自己跑 p0/p4 对照再决定。
3. 后续候选（属于 L2 剩余项，另开 PR）：per-module 完成信号替代轮询、`spaceEpoch + cv.wait_for` 的有界阻塞、槽内轮转与 turn 预算、`blockedRounds/idleRounds/turns` 更细的可观测。

## 后果

- 不会为了一个“平台相关、可回退”的差距去改默认路径或计数协议。
- 用户如果开池化，代价是可预期的（Windows 深链 −43%），文档里能查到原因与数字。

## 未验证

- Windows 电源方案（当前是“平衡”）与核心停泊对共享槽唤醒延迟的影响；
- Windows 调度器把被 `Pause()` 占满的槽重新调度的延迟，与 WSL2 的差异；
- `Pause()` 自旋期间同槽其他 worker 拿不到执行机会这一结构性问题的上限。

## 什么时候该重看

- Windows 深链 pool 4 稳定达到 p0 的 85% 以上；
- 或者 L2 剩余四项落地后仍无改善——那时应重新评估“池化是否值得保留”。
